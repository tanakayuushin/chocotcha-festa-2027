# チョコっちゃ公式サイト 制作スキル

## 1. 作業の順番（毎回この順）
1. **正本を先に読む**: CLAUDE.md →（文面を変えるなら）Drive の HP内容修正案 v1_r3。決まりに無い文を足すときは「オーナー指示」と CLAUDE.md に記録する
2. **中身を先に決め、見た目はあと**: 載せる文・数字・リンク先が確定してから配置を考える。未確定は「予定／計画中／準備中」の文字ラベルで示し、空欄やダミー文字を置かない
3. **build.py だけを編集**: HTML は生成物。CSS はトークン（`:root` の変数）を使い、新しい色・角丸・影を増やさない
4. **再生成 → 検査 → 画像で確認 → 作業ブランチへ push**: 検査は下の「7」。画像を自分の目で見てから報告する。見ずに「できました」と言わない
5. **公開はオーナーの「公開して」のあと**: `main` には公開用ファイルだけ。CSS/JS を変えたら `VER` を上げる

## 2. デザインの物差し（この順で優先）
- **読めること** > **迷わないこと** > **かわいさ**。文字は本文 14.5px 以上、色のコントラストは本文 4.5:1 以上
- **1区画に主役は1つ**。目立たせたいものにだけ朱（`--red`）とずらし影を使う。朱のベタ面は作らない
- **カードは3種類だけ**: 押せる（こげ茶の輪郭＋影＋矢印）／押せない（`--line2` の平らな枠）／主役（ビター→こげ茶のグラデ）。4種類目を作らない
- **同じ意味のものは同じ形**: 例）トップとページで同じ名前の区画は同じ見た目にする
- **同じ区分は件数に関係なく同じ形**（オーナー決定 2026-11-11）: 協賛は1社目からロゴ一覧、特別協賛・会場協力は紹介カード、協力・後援は名称のタグ。件数で見せ方を切り替えない
- **装飾は周縁にだけ**（リボン・紙・ストライプ）。チョコの絵は使わない

## 3. 協力・協賛の載せ方（イベント運営の基本）
- 目的は2つ: すでに協力してくれた人への**きちんとしたお礼**と、これから協力する人への**安心材料**（誰が入っているか、どう紹介されるか、どこに連絡するか）
- **区分**: 会場パートナー／特別協賛／協賛／協力／後援。上の区分ほど大きく。同じ区分の中は順不同・敬称略と明記
- **載せる条件**: 先方の承諾、名称の表記、リンク先URL、ロゴの使用許諾（ロゴは透過PNGかSVG）。そろっていない項目は載せない（ロゴが無ければ頭文字の仮ロゴで出せる）
- **リンク**: 先方サイトへは `rel="sponsored noopener"`、別タブ。協賛（special/sponsor）は JSON-LD の `sponsor` にも入れる
- **紹介のしかた**（主催が決められる範囲だけを約束する）: 会場パートナー＝ロゴ・紹介文・リンク／特別協賛＝大きなロゴ・紹介文・リンク／協賛＝ロゴ・リンク／協力＝名称・リンク／後援＝名称。金額・当日の掲示などは要項確定後
- **置き場所**: トップ（お知らせの下）に「協賛・協力」、お問い合わせページの協力欄に「ご協賛・ご協力いただいている皆さま」＋「ご協力のかたち」。募集の案内（相談ボタン）とセットで置く
- **見出しの言い方**: 一覧の見出しは慣例どおり名詞形「協賛・協力」「後援・協賛・協力」。相手の行為には「ご協賛・ご協力」と「ご」を付け、「皆さま」はひらがな混じり（公式サイト本文の柔らかい調子に合わせる）。「一緒につくっている」のような主催目線の言い方は、協力者を同列に扱う印象になるので見出しには使わない
- データは `tools/build.py` の `SUPPORTERS`。1件＝ tier / name / url / desc / badge / logo

## 4. 文面の物差し
- 用語: 出店・出演・来場・出場。「参加」は企画に加わる意味だけ
- 1文は短く、主語と述語を近く。「〜を予定しています」「〜は決まり次第お知らせします」で未確定を示す
- 数字・制度は一次ソースで確認。確認できないものは載せない

## 5. 検索で見つかるために
- 本文に「山口市・湯田温泉・バレンタイン・チョコ・イベント・2027」が自然に入っていること（題名と説明文だけでは足りない）
- 各ページの `<title>` は「ページ名｜サイト名」、説明文は 80〜120字で日時・場所・入場無料を含む
- 構造化データ: WebSite ＋ Festival（開催予定＝EventScheduled、入場無料＝offers price 0）。協賛は `sponsor`
- 更新したら sitemap の lastmod と更新日（`UPD_*`）を変え、Search Console で再送信を依頼する

## 6. 計測
- 置き場所ごとの専用URL（UTM）を使い分ける。既存: Instagram／チラシQR／Googleフォーム／市報（QRと印字URL `chocotcha.jp/shiho`）
- 新しい置き場所が増えたら `tools/make_qr.py` の TARGETS と `build.py` の REDIRECTS に足し、CLAUDE.md の UTM 一覧を更新する
- 測るのは「来た数」より「申込みページへ進んだ数（go_apply）」と「メール・Instagram を押した数」

## 7. 公開前の検査（全部通ってから報告）
```
python3 tools/build.py .                       # 生成
node <scratch>/ovf.js                           # 8ページ×6幅で横はみ出しなし
node <scratch>/check.js（要 http.server 8765） # 内部リンク・アンカー・JS無効・メニュー
grep -l '第1回\|決定\|18:30\|100席\|5,000円〜\|前日18時' *.html   # 旧文言ゼロ
python3 -c 'json.loads(JSON-LD)'               # 構造化データが読める
```
- 変えた区画は PC（1280）とスマホ（390）の画像を撮り、自分で見てから送る
- 修正案の文を変えたときは、変えた理由を CLAUDE.md に1行残す

## 8. AI がサイトを作るときに崩れやすい点（自戒）
- 指示が曖昧だと既定の見た目に戻る → トークンとカード3種類の決まりを先に読む
- 似たコードを増やしがち → 同じ部品は関数（`ph`, `sec_head`, `supporters_html`）に寄せる
- 「できた」と言いたがる → 画像と検査結果を出してから言う
- 参考サイトを見ずに想像で作りがち → 開けないときは「開けなかった」と言い、要点だけ検索結果から取る
